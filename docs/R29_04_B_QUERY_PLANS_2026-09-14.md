# R29-04-B — Bounded query-plan assessment (2026-09-14)

## Outcome and scope

A reproducible local SQL assessment identifies a **candidate**, not an approved migration:
`patient_observations(practice_id, patient_id, observed_at DESC, created_at DESC, id DESC)`.

On the measured synthetic fixture this index eliminates the observation page's temporary ORDER BY B-tree. It does not remove the latest-snapshot correlated subquery, nor the aggregate count over remaining eligible source scope. No runtime SQL, schema migration, authentication, decryption, clinical completeness or feature flag changed. R29-04 remains incomplete.

The assessment script reads actual observation-reader SQL templates and cursor predicate, fails on unexpected template shape, and executes them against an isolated in-memory SQLite database. It accepts no database path/credentials and makes no network requests. The hypothetical index exists only until the process closes. This is not a D1 migration rehearsal.

## Other findings from direct source (not measured query plans)

- History continuation first calls readPatientCoreSummary, which performs registry, identifiers, demographics and latest-encounter reads; the caller uses the returned summary only as an existence gate. A later bounded optimization could retain the scoped registry lookup while avoiding unused reads/decryption, but current failure behavior (including demographics corruption) must be explicitly tested before changing it. This packet does not implement that change.
- Observation COUNT has no LIMIT and retains a correlated MAX(revision) lookup. The existing unique encounter/revision index is used for snapshots in this fixture; adding another snapshot index without evidence is not justified.
- Encounter timeline ordering uses a prefixed-ID expression; order timeline joins plans and evaluates fulfillment/result subqueries. These remain a **separate measurement scope**, not an asserted indexing fix.
- No proposal removes rejected/raw exclusion accounting, sourceVersion predicates, tenant predicates, stable cursor ties, or historical revision rules.

[Cloudflare's index guidance](https://developers.cloudflare.com/d1/best-practices/use-indexes/) recommends verifying plans and actual read/write metadata; index maintenance also affects writes. We use it for method, not as proof that this candidate benefits GLYMIZE production.
