# R29-03-B — session-bound transport decision

2026-09-14. Bounded High review complete. **Conditional design, transport implementation deferred**; A remains implemented locally and OFF. Supplements [R29-03 consistency](D1_READ_CONSISTENCY_R29_03.md). No auth, client, CORS, configuration or provider change in this packet.

## Decision and usefulness gate

Do not add a browser bookmark header to the current history flow merely to round-trip it. Every approved clinical history request still starts `first-primary`; a bookmark is a lower bound, not proof of current clinical status. The current flow already anchors to primary without a transported hint. Header encoding, encryption/verification and lifecycle handling would add work without eliminating that anchor. This is an architecture inference, not a measured performance result. [Cloudflare session semantics](https://developers.cloudflare.com/d1/best-practices/read-replication/).

**Defer B wire implementation until a named, reviewed consumer can use a bookmark floor and has a credible measurable benefit.** Do not relax mutable clinical freshness to manufacture such a consumer. This narrows sequencing, not the approved R29 scope: read replication, cross-request consistency acceptance and RC evidence remain on the Roadmap. A's within-request session can still be measured independently. No dummy encrypted-envelope library or global browser interceptor is needed now.

The conditional contract below resolves the preflight questions; it is not permission to activate a bookmark-only clinical route. Next implementation checkpoint moves to approved **R29-04-A / Astra Medium**, measuring request-owned CryptoKey reuse in bounded clinical reads, preserving AAD/key rotation and avoiding shared PHI state. No index migration or unbounded concurrency is implied.

## Verified integration evidence

- `platform-index.ts`: `AccessPayload` contains userId, practiceId, sessionId and expiresAt. `requireRuntimeUser` checks the matching refresh-token row and current user using the original database. `issueSession` creates a new sessionId; refresh consumes the parent and issues a child. **Use the exact verified sessionId, never the longer-lived family_id.**
- `platform-v3-session.ts`: the access payload has the same session identity; its runtime guard also checks primary revocation/expiry. Neither client-supplied actor labels nor a bookmark can replace either guard.
- `patient-record-v2/context.ts` / facade in `platform-index.ts`: only user/clinical secret/authorization closure are currently passed, not session identity. A future transport adapter must receive a minimal verified consistency scope separately; do not widen every reader's authority or pass raw bearer/refresh tokens.
- `runtime-client.ts`: initial/401/admin sends rebuild from the same init.headers. Session storage/adoption and clearing emit a generic auth event; that event is not itself a server-verified generation. A future hint cannot be supplied once in init.headers and blindly replayed by the retry closure.
- `runtime-security.ts`: existing sealPayload/openPayload use context-derived non-extractable AES-GCM keys and random 12-byte IVs. The auth wrapper accepts an active/previous/legacy key set. The future hint purpose must be separate and need not inherit that permissive key-acceptance set.

These are bounded source observations, not an exhaustive authentication audit or a finding of an existing bookmark leak. No bookmark header is connected today.

## Conditional server contract

1. Authenticate and authorize first on the original primary path. Derive an immutable internal scope from **verified** access.userId/practiceId/sessionId, matched to current user/practice. Carry the verified access expiry and matching refresh-row expiry; envelope expiry is their minimum. Reject invalid/non-finite timestamps. Existing revocation checks run on every request regardless of envelope validity; no offline lease is introduced.
2. Add trusted deployment-owned logical runtime audience and database epoch. Audience identifies the runtime endpoint, including gateway/base-path mapping; epoch identifies this database incarnation and changes on restore/rebinding/rollback. Do not derive them from arbitrary Origin/Host/forwarded headers or permit the client to choose them. Missing configuration disables hint use/issuance and keeps primary reads. Browser endpoint changes independently invalidate its local chain.
3. The exact allowlisted route supplies patient scope and family from validated input. Envelope claims are version, purpose, audience, database epoch, actorId, practiceId, exact sessionId, patientId, family, issuedAt, expiresAt and opaque bookmark. No names, clinical facts, access tokens or refresh tokens. Reject unknown versions/purposes or scope mismatch; do not equate history sourceVersion/cursor with the D1 bookmark.
4. Reserved application header: `x-glymize-d1-read-hint`, only if the future consumer is enabled. Encode an authenticated **encrypted** envelope, not plaintext JSON plus a MAC exposing session/patient identifiers. Reuse the reviewed AES-GCM primitive with the active auth sealing root and distinct key-derivation purpose `D1-READ-HINT-V1`; protect the version/purpose through authenticated content and require exact matching after decryption. Fresh random IV per issuance. No reuse of runtime-access, patient-cursor or offline-grant domains. Prefer an unknown parsed payload followed by an explicit bounded validator, not a generic type assertion.
5. Open hints with the active root only; key rotation deliberately resets hints. Do not reuse openAuthPayload's previous/legacy acceptance policy for consistency hints. No new root secret or shared key cache is provisioned by this design. A future primitive substitution requires preserving encryption, integrity and domain separation.
6. Maximum header envelope is an initial local engineering budget of 4096 bytes, including encoding overhead; enforce before decoding/decrypting. Validate segment counts/encoding/IV and all bounded claims. Never truncate a provider bookmark; if it cannot fit, omit issuance and retain a fresh-primary next read. Real bookmark sizes remain an RC gate.
7. Missing, malformed, tampered, expired, wrong-scope/epoch or unsupported hints are **rejected as hints**, with primary reset after normal authorization; they are not new authentication failures. Never execute a query with such a bookmark. Provider/query failures retain bounded explicit failure: no mutation retries or merging partial data with a fallback result. Log only fixed reset categories/counts, never header/claim/bookmark/error contents.
8. Obtain the final bookmark only after all scheduled reads succeed. Issue only on a successful participating read; no header on auth/error/other routes. Do not retrofit legacy write transactions to mint one. Current clinical routes remain first-primary even if transport is introduced for another consumer.

## Conditional client lifecycle ownership

- The patient/read client owns a bounded per-view, per-family chain (not a process/global patient map). Key it to canonical runtime endpoint, server-advertised epoch, actor/practice, patient, family and **tab-local auth generation**. The encrypted envelope is opaque to browser code; no parsing, lexical maximum, numeric comparison, persistent storage or cross-tab sharing.
- The runtime transport owns credential-attempt boundaries. In an explicit participating-read option, it builds each attempt's headers afresh, strips any caller-supplied reserved hint, and supplies a chain hint only when the attempt generation still matches. Unrelated runtime calls retain their behavior. Admin fallback never participates or inherits a clinician hint.
- A first 401 invalidates the old chain **before** refresh. A successfully refreshed safe GET may be retried once with no hint under the new generation; the old operation's result/bookmark must not be delivered to the old view. The view can initiate a fresh authorized read. No additional retry of writes and no change to existing write idempotency/rotation semantics.
- Login/adoption/logout initiation, session clearing, credential refresh, actor/practice/endpoint changes and admin fallback invalidate generation. Invalidation is distinct from existing presentation/auth-event policies: do not redefine same-actor UI identity or R28 handoff authority. It must happen even when a refresh result will later fail.
- Serialize participating reads in each chain, including response-body parsing/validation and bookmark adoption. Retain generation/request identity through UI application, not just through fetch resolution. Abort plus discard obsolete results; abort alone is insufficient because a response may already be buffered. Dispose on view unmount. Separate tabs/devices always bootstrap fresh-primary.
- Relevant write **start** invalidates all affected chains immediately; reads are blocked/discarded while overlapping writes remain unsettled. Track overlapping writes so the first completion cannot clear the barrier for the second. Success requires acknowledged commit before a new primary read; ambiguous/failing completion clears hints and requires authoritative reconciliation. Never infer that cancellation undid a write. Uninstrumented write paths are an activation blocker for a consumer, not a reason to guess their outcome.
- Missing/oversized/invalid response hints clear the chain; never retain an older hint silently. A restored database/epoch change resets local state without comparing opaque bytes. Do not attach hints to public/offline caches or use them to reopen protected offline data.

## CORS, gateway and acceptance gates

Allow/expose only the exact reserved header on the enabled participating path and already permitted origins, with matching OPTIONS behavior. The fixed-upstream gateway must retain no-store and forward only the intended route/header contract; do not reflect arbitrary headers or broaden origins. Confirm logging/tracing/proxy middleware do not capture the header. No CORS or gateway edits before a consumer passes the usefulness gate.

Before B implementation/activation: name the consumer and its freshness semantics, map its writes and view lifecycle, then test missing/stale/tampered/wrong-scope/oversized hints, active-root rotation, session refresh/revocation, database restore, late bodies/UI application, overlapping writes, ambiguous commits, admin fallback, multi-tab bootstrap, gateway/CORS and rollback. Re-run relevant real workerd/RC tests plus CPU/rows/latency comparisons. Synthetic tests alone cannot establish replica lag or speedup.
